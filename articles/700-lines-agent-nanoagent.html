一句话结论一个成熟的 Agent 核心只有三件事：把函数变成 LLM 能调用的工具、让模型在「思考→调工具→看结果」的循环里反复迭代、把每一步可靠地记进上下文。这三件事完全可以在 700 行 Python 内自洽实现，NanoAgent 就是这样一个极简但完整的框架。

1为什么需要手写一个 Agent 框架

主流的 Agent 框架（LangChain、Google ADK、OpenAI Agents）功能很全，但都带着较厚的抽象层：回调、Pydantic 校验、多模态消息、缓存、记忆管理……对只想「把 LLM + 工具跑通」的场景，这套抽象反而抬高了理解成本。

手写一个极简框架的用意不在「替代它们」，而是用最小闭环讲清楚 Agent 的本质：工具注册、主循环、上下文这三块一旦亲手实现过，再翻任何框架文档都会快很多——它们其实是同一件事的不同封装。

2核心架构：700 行如何组织一个 Agent

NanoAgent 的 src/nanoagent/ 只拆成 6 个职责单一的文件，彼此解耦又能拼成一个完整闭环：

src/nanoagent/# 六个文件对应六层职责
agent.py    # Agent 本体：指令 + 工具 + 系统提示聚合
tool.py    # Tool 抽象 + @function_tool 装饰器 + JSON Schema 生成
runner.py   # Runner：reAct 主循环（思考 → 调工具 → 看结果）
context.py  # Context：消息历史 / Token 统计 / 工具调用记录
model.py    # Model 抽象基类 + OpenAI 实现 + 流式协议
mcp_tool.py # MCP 集成：把 MCP 服务器导入成统一工具组

以 Agent 为例，它只是一个 dataclass，负责「描述一个智能体」而非「执行」。真正的执行在 Runner：

agent.py（节选）@dataclass
class Agent:
    name: str
    instructions: str                    # 角色指令
    model: Model | None = None       # 默认 OpenAI
    tools: list[Tool | MCPToolGroup] = default_factory(list)

    def get_system_message(self) -> dict:
        system = self.instructions
        if self.tools:
            names = [t.name for t in self._get_all_tools()]
            system += f"\n\n你可以使用以下工具: {', '.join(names)}"
            system += "\n当需要使用工具时，请调用相应的函数。"
        return {"role": "system", "content": system}

    def get_tools_schema(self) -> list[dict]:
        return [t.to_dict() for t in self._get_all_tools()]

关键点：get_tools_schema() 把工具列表换算成 OpenAI 兼容的 function-calling schema 交给模型，模型据此决定「该调哪个工具、传什么参数」。整条链路的输入输出都是普通字典——这正是它能保持轻量的原因。

3工具系统：把普通函数变成 LLM 工具

工具系统的核心是 从函数签名自动推导 JSON Schema。借助 inspect.signature 和 get_type_hints，一个普通 Python 函数加个装饰器就变成 LLM 可调用的工具：

tool.pydef function_tool(func=None, *, name=None, description=None):
    def decorator(f):
        tool_name = name or f.__name__
        desc = description or f.__doc__ or f"Function {f.__name__}"
        return Tool(tool_name, desc, f)
    return decorator(func) if func else decorator

class Tool:
    def _generate_schema(self) -> dict:
        sig = inspect.signature(self.function)
        hints = get_type_hints(self.function)
        properties, required = {}, []
        for pname, p in sig.parameters.items():
            if hints.get(pname) is int:  ptype = "integer"
            elif hints.get(pname) is float: ptype = "number"
            elif hints.get(pname) is bool:  ptype = "boolean"
            else:                              ptype = "string"
            properties[pname] = {"type": ptype}
            if p.default is inspect.Parameter.empty:
                required.append(pname)
        return {"type": "function",
                "function": {"name": self.name, "parameters":
                    {"type": "object", "properties": properties, "required": required}}}

这样带来的两个直接好处：

  • 零配置接入：不需要手写 OpenAI 的 tools 结构，工具函数本身就是描述。
  • 有默认值即可选：通过 param.default is inspect.Parameter.empty 自动判断必选参数，让模型知道哪些参数必须给。
用法
@function_tool
def get_weather(city: str) -> str:
    """查询某城市实时天气"""
    return fetch(city)

agent = Agent(name="assistant", instructions="你是助手",
               tools=[get_weather])

4运行引擎：reAct 主循环如何执行

Agent 的「智能」来自 reAct 模式：模型先给思考/工具调用 → 框架执行工具 → 把结果回填上下文 → 再让模型继续，直到它给出最终答复。NanoAgent 的 Runner.run_stream 就是这个循环：

reAct 主循环 · 单轮流程

Step 1in用户输入 → 追加到上下文
Step 2llm模型流式生成 → 增量回答 / 工具调用
Step 3tool若含 tool_calls → 解析参数 → 查找执行
Step 4ctx工具结果 add_tool_call 回填 → 回到 Step 2
Exitans无 tool_calls → 输出最终回答并返回

执行的核心代码：

runner.py · run_stream（节选）for turn in range(max_turns):
    # 1. 把当前消息交给模型，得到流式增量
    stream_gen = agent.model.generate_stream(messages, tools_schema)
    full = ""; response = None
    for item in stream_gen:
        if isinstance(item, ModelResponse): response = item; break
        if item.content: full += item.content; yield answer_delta(item.content)

    # 2. 无工具调用 → 直接给出最终回答
    if response and not response.tool_calls:
        context.add_message("assistant", full)
        return RunResult(full, context)

    # 3. 有工具调用 → 逐个执行并回填
    for tc in response.tool_calls:
        tool = agent.find_tool(tc["function"]["name"])
        result = tool.execute(json.loads(tc["function"]["arguments"]))
        context.add_tool_call(tool.name, args, result.result)  # 回填

几个有工程味道的细节：

  • 最大轮次兜底：max_turns 默认 10，防止模型在工具循环里出不来。
  • JSON 容错：模型偶尔返回不合法 JSON 参数，先 json.loads，失败再回退 eval，再失败给空参。
  • 失败结果也是事件：工具找不到、执行报错都会以 ERROR 事件暴露，而不是静默吞掉——这对调试很关键。

5上下文管理：对话历史与 Tool Result

reAct 循环能否收敛，取决于工具调用及其结果是否正确写入上下文。OpenAI 的 tool-calling 协议要求：assistant 消息携带 tool_calls，且每个 tool_call 都要有对应的 role=tool 结果消息。Context 把这个协议封装成 add_tool_call：

context.py · add_tool_calldef add_tool_call(self, tool_name, arguments, result):
    # 若上一条 assistant 已有 tool_calls → 追加；否则新建一条
    for last in messages_check:
        # 合并「上一段思考内容 + 本次工具调用」到同一条 assistant 消息
        ...
    # 追加 role=tool 的返回值消息，与 tool_call_id 绑定
    self.messages.append({
        "role": "tool", "name": tool_name,
        "content": result, "tool_call_id": tid})

这一层还顺带管理了多轮对话的延续：context 在多次 run() 之间复用时，消息历史被保留，模型能看到之前的对话与工具结果，从而形成连贯的多轮 Agent。Token 用量也在这里累加统计（Usage）。

6模型抽象与流式输出

框架只依赖 Model 抽象基类，默认实现 OpenAIModel。这意味着任何兼容 OpenAI Chat Completions 协议的服务（含本地 Ollama、各种网关）只要配一个 base_url 就能接入：

model.pyclass Model(ABC):
    @abstractmethod
    def generate(self, messages, tools=None) -> ModelResponse: ...
    def generate_stream(self, messages, tools=None):   # 可选
        # 默认实现：整段生成后逐字符 yield

class OpenAIModel(Model):
    def __init__(self, model=None, api_key=None, base_url=None, **kw):
        self.model_name = model or os.getenv("MODEL", "gpt-3.5-turbo")
        self.api_key = api_key or os.getenv("API_KEY")
        self.base_url = base_url or os.getenv("BASE_URL")   # 兼容本地/网关
        self.client = OpenAI(api_key=self.api_key, base_url=self.base_url)

流式输出通过 StreamEvent 暴露，类型包含 QUESTION / THINKING / TOOL_CALL / TOOL_RESULT / ANSWER / ANSWER_DELTA / ERROR。前端或终端可以据此渲染「正在思考」「正在调用工具」这类实时状态，而不是干等最终结果。

7MCP 集成：接入外部工具生态

真正让这个 700 行框架「不小」的，是它对 MCP（Model Context Protocol） 的原生支持。MCP 把外部工具（地图、数据库、办公套件等）标准化成可独立启动的服务器；NanoAgent 用 MCPClient 连接一个 MCP server，并把它包装成和本地工具同构的 MCPToolGroup，从而混用两种工具：

mcp_tool.py（用法）pool = MCPToolPool()
amap = await pool.add_mcp_server(
    "amap",
    command="npx", args=["-y", "@amap/amap-maps-mcp-server"],
    tools=["search_location"])          # 可选，默认导入全部

agent = Agent(tools=[calculate, amap])    # 本地函数 + MCP 工具组混用

对比直接写死某个第三方 API，MCP 带来的价值是统一接入协议 + 进程隔离：每个 MCP server 是独立进程，崩溃不影响主框架；工具名、参数 schema 由 mcp.initialize 协商出来，框架只需把 MCP 工具映射成自己的 Tool 即可。

取舍MCP SDK（mcp>=1.12）是运行时可选依赖——不装也能用纯本地工具，装了才启用 MCP 能力。这是「轻量」与「可扩展」之间的刻意平衡，符合小框架「按需加容量」的原则。

8总结：学到什么，能怎么用

  • ✓ 一个 Agent = 系统提示 + 工具 schema + reAct 主循环 + 上下文，四者缺一不可但都可独立替换。
  • ✓ 从函数签名自动生成 JSON Schema，是工具系统「零配置」的关键。
  • ✓ 流式事件让「思考中 / 调工具中」可见，用户体验远好于等待整段返回。
  • ✓ 薄抽象 + 按需依赖，核心 700 行，却能通过 MCP 对接任意工具生态。
对想真正理解 Agent 的同学，我建议先手写一个十几轮能跑的 mini 版，再回头看框架文档——你会发现大部分「魔法」都只是这套模式的封装。NanoAgent 提供了可读性极高的参考实现。
