把收藏视频变成可对话知识库：
ClipMind 的架构与工程取舍

一句话结论ClipMind 把「我收藏过的视频」变成可语义检索、可对话追问的个人知识库：同步收藏夹 → ASR 语音转写 → 向量入库 → RAG 问答并追溯来源。全程本地优先，第三方 Key 与模型均可替换为本地方案，数据不出本机。

1背景：收藏夹为什么总是「吃灰」

大多数人都有这样的收藏夹：几百条 B 站视频、抖音喜欢列表，收藏时觉得「以后要看」，但几乎不会再看第二遍。它们散落在两个平台、以音视频形态存在，既无法全文搜索，也无法归纳回顾。

ClipMind 的核心洞察：这些视频里其实是半结构化的高价值内容——只要把它们转写成文字、向量化入库，就能像查资料一样「搜」和「问」。于是定了四个核心能力：

  • 自动同步：扫码登录后拉取 B 站收藏夹、抖音喜欢列表。
  • ASR 转写：把视频语音转成文字，形成可检索的文本切片。
  • 向量知识库：文本分块 → 向量化 → 存入 ChromaDB。
  • RAG 对话：对知识库提问，回答带视频来源引用。

2整体数据流与边界

整个系统的数据流可以画成一条「入库链路」+ 一条「问答链路」，两条链只在「向量库」处交汇，职责非常清晰：

ClipMind 两条主链路

入库链路平台API→抓取→ASR→分块→嵌入→ChromaDB
问答链路提问→混合检索→RRF→LLM→回答+来源

从目录结构能看出后端的模块化程度很高：app/services/ 下按职责拆分出 asr.py（转写）、bilibili.py（B 站拉取）、hybrid_retriever.py（混合检索）、rag.py（问答）、ingest_pipeline.py（入库调度）等十几个服务；routers/ 暴露 FastAPI 路由；前端是 Next.js + Tailwind，后端 FastAPI + ChromaDB。

3平台同步：B 站/抖音的增量拉取

对接平台 API 的核心难点是登录态与增量同步。B 站侧用扫码登录（优先 API 方式生成二维码，失败回退浏览器池），拿到会话 Cookie（如 SESSDATA）后再请求收藏夹。

增量同步的实现值得单独说——它用「按收藏时间倒序 + 命中边界即停止」来避免重复拉取：

bilibili.py · get_all_favorite_videosasync def get_all_favorite_videos(self, media_id, last_sync_at=None):
    incremental = last_sync_at is not None
    for pn in count(1):
        result = await self.get_favorite_content(media_id, pn=pn, ps=20, order="mtime")
        medias = result["medias"]
        if incremental:
            for m in medias:
                if m.get("fav_time", inf) <= last_sync_at:
                    return   # 命中已同步边界，后续更老，提前停止
                yield m
        else:
            yield from medias
        if not result["has_more"]: break
        await asyncio.sleep(0.3)      # 控制请求频率，避免风控
  • 增量非全量：只同步fav_time > last_sync_at 的新增视频，大幅节省请求与入库成本。
  • 边界兜底：遇到缺失 fav_time 字段的视频，保守纳入而不是跳过，避免漏同步。
  • 限速：每页间 sleep(0.3)，属于对接第三方 API 的基础卫生。

4ASR：从视频到可检索文字

视频内容无法直接向量化，必须先经 ASR 转成文字。ClipMind 对 ASR 做了云端 / 本地双模式：

  • 云端（DashScope Recognition）：本地文件直传，返回带时间轴的句子列表，转写质量高。
  • 本地（faster-whisper）：无需网络、数据不出机，适合离线与隐私场景。
asr.py（节选）class ASRService:
    def _configure(self):
        if not self.api_key: raise ValueError("未配置 DASHSCOPE API Key")
        dashscope.api_key = self.api_key   # asr_api_key 独立，不复用 LLM key

    def _transcode_audio_to_pcm(self, file_path):
        # ffmpeg 转成 16k/s16le/单声道 PCM，适配 Recognition
        cmd = [ffmpeg, "-i", file_path, "-f", "s16le",
                "-acodec", "pcm_s16le", "-ac", "1", "-ar", "16000", pcm_path]
        result = subprocess.run(cmd, timeout=120)
        return pcm_path if result.returncode == 0 else None

一个容易踩的工程细节：ASR 的 Key 与 LLM 的 Key 必须分离。代码里明确注释「ASR 使用独立的 asr_api_key，不复用 openai_api_key」，否则在只配了本地 LLM 时会被误调 DashScope 发起无效 401 请求、白耗等待。这种「配置源解耦」是双模式系统里很容易被忽略的坑。

5向量化：多提供方 Embedding 与本地优先

Embedding 与 LLM 一样做了多提供方抽象，通过 RAGService._VALID_PROVIDERS 约束合法集合：

rag.py · Embedding 提供方_VALID_PROVIDERS = {"openai", "dashscope", "ollama", "nvidia", "local"}
# 支持云端 API 与本地模型（bge/m3e、ONNX 运行时离线推理）

亮点是 local 这个「本地 Embedding」提供方：用 sentence-transformers 加载 bge/m3e 一类模型，并通过 onnxruntime 离线推理（不依赖 torch，体积小、发布版能跑）。这样在没有网络、没有第三方 Key 的环境下，整个入库链路也能本地跑通——与项目「本地优先」的定位一致。

rag.py · LLM 双模式if llm_provider == "ollama":

else:
    self.llm = ChatOpenAI(api_key=cfg.openai_api_key, base_url=cfg.openai_base_url)

6问答链路：混合检索 + RRF + 来源追溯

回答质量的上限取决于检索质量。ClipMind 在 RAG 问答处用了 混合检索 + RRF 融合：

  • 向量检索：语义召回（hybrid_retriever.py）。
  • 关键词检索（BM25 类）：精确匹配，对专有名词、代码片段更可靠。
  • RRF 融合：用倒数排名融合两条结果，抑制单一来源的偏科。
为什么混合不止向量纯向量可能对「产品型号、术语、人名」这类精确 key 召回不稳定；加一路关键词检索并用 RRF 融合，能同时保住语义相关与精确命中，这也是我上一篇里验证过的方向（命中率 9/12 → 12/12）。ClipMind 把它落到了视频知识库这种长文本切片场景。

最后是来源追溯：每个回答都尽量带上命中的视频片段来源，让用户可以一键跳回原视频。这一层对「知识库工具」至关重要——没有出处的回答，可信度会大打折扣。

隐私说明项目是本地优先架构：ChromaDB 落库在本机、数据库用 SQLite、Cookie 与敏感配置字段服务端加密存储；可选本地 ASR 与本地 Embedding 后，可以在完全不联网、不上传第三方的情况下完成入库与问答。第三方对接仅在你主动配置 Key 时启用。

7工程取舍：本地优先、任务幂等、双模式模型

如果把 ClipMind 当作一个「工程范本」来看，值得吸收的是几个系统级取舍：

  • 变与不变分离：Embedding / LLM / ASR 各走独立提供方抽象，新增一个提供方只加一个分支，不动核心链路。
  • 配置按需解耦：ASR key、LLM key、Embedding key 各自独立，避免「配了一个就强制依赖另一个」。
  • 入库任务可追踪：ingest_pipeline / task_tracker 把每次入库做成可幂等、可恢复的任务，而不是一次性脚本。
  • 失效隔离：ASR 云服务挂掉时能回退本地 Whisper——用「降级路径」保住了整条链路的可用性。
ClipMind 真正的价值不只是「把视频转文字」，而是示范了一个面向个人的 AI 工具，如何把「必须联网调三方」的产品做成「默认本地、可选云端」。对想用 RAG 落地私有数据的项目，这套提供方抽象与双路径设计很值得参考。
