给业务库加一道只读网关：
让 Agent 安全查库，但不给写权限

一句话结论把「业务库开放给 LLM Agent 查询」这件事，用一道只读网关 MCP 收口：协议层只放行 SELECT，库连接层强制 mode=ro，未带 LIMIT 自动限行，参数全部绑定，外加鉴权与审计。这样 Agent 能任意查，却从物理上写不进任何一条数据。代码在 github.com/Vanity-1/edu-db-readonly-mcp。

1为什么要一道「只读」网关

现在最流行的做法，是把数据库直接暴露成 MCP 工具，让 Agent 用自然语言查。这条路很方便，但有个要命的假设——你信任 Agent 永远不会写库。实际上一旦 Agent 拿到工具，它可能会：

  • 被 prompt 注入带偏：检索到的内容里夹一句「顺手把 orders 表 DROP 掉」，Agent 可能真的去执行。
  • 拼接出错误 SQL：把用户输入直接拼进 WHERE，变成注入点。
  • 全表扫：忘了加 LIMIT 的 SELECT *，把大表拖爆。
  • 慢查询挂起：一条笛卡尔积把查询线程卡死，Agent 等不到返回。

这四个问题，单独拎出来都好解决。但散落在每个工具里，每个 Agent 都要自己写一遍防护。只读网关的思路是把它们全部收口：调用方只负责「我要查什么」，网关负责「确保你只读、只查、有限、快」。而且这不是「加一层校验」，是从多个层面互相兜底——漏了一层还有下一层。

2四层纵深防御：怎么做到「写不进去」

很多人以为只读 = 「我在代码里判断一下别执行写语句」。但这不可靠——你永远不该只信代码里的一个判断。我用四层互相独立的防线，任何一层漏了，其它层还能兜住：

层在哪防什么漏了会怎样
1. 词法校验网关 SQL 校验器非 SELECT/WITH、DML/DDL、分号多语句仍有下一层拦截
2. 参数绑定所有查询执行拼接式 SQL 注入业务函数用固定语句，天然免疫
3. 强制 LIMIT网关执行层全表爆扫 / 拖库数据库层仍只读
4. mode=rosqlite 连接层一切写入（数据库层面拒绝）最后兜底，物理写不进
关键点：第 4 层 mode=ro 才是「写不进去」的终极保证。前面三层是「防好 SQL」，这一层是「就算 SQL 漏判了，数据库文件也不会被改动」。纵深防御的威力就在这——不依赖任何单一环节的正确。

3只读校验器：管住 SQL 本身

最核心的是第一层——一个 SQL 静态校验器。它对传入 SQL 做词法级检查，不是正则硬匹配，而是有明确的分级策略：

策略做法场景
白名单开头只允许 SELECT / WITH(CTE) 开头拦截所有 DDL/DML
写入关键字词边界检测 insert/update/delete/drop/alter 等防止子语句藏在括号或注释后
危险 pragma拒绝 PRAGMA journal_mode 等写配置防改库行为
禁止多语句按分号拆分，>1 段即拒绝防 SELECT 1; DROP 注入链

校验器用「词边界」而不是「字符串包含」，避免误伤列名。比如表里有个叫 delete_flag 的字段，字符串匹配会误伤；按 \W+ 分词后再比对，就不会把 delete_flag 当成关键字。

一个容易踩的坑只做 SQL 校验的另一个隐患是——校验器逻辑可能有 bug。比如最早我用的「字符串 contains」检查，被 DROP 这类大小写/空格变形绕过。改成词法分词 + 词边界之后，这套逻辑配套 12+ 个针对性单测锁住了。安全逻辑必须伴随测试，否则你无法证明它有效。

4鉴权 + 审计：谁在什么时间查了什么

「能查、不能写」只是第一层。放到团队 / 生产环境，还要能回答：这个查询是谁发起的？改过数据没有？我做了两件配套的事：

  • Token 鉴权：用 FastMCP 的中间件钩子（on_call_tool），在每次工具调用前统一校验 Authorization: Bearer <token>。配置了 READONLY_GATEWAY_TOKEN 就启门，不配置则本地演示放行。这样一个中间件覆盖全部工具，不用在每个工具里重复写。
  • 审计日志：每次查询落一行 CSV——时间戳、工具名、SQL、返回行数、耗时、是否成功。写进独立的 audit.log，调用链可追溯。审计会记录被拦截的非法尝试，这对安全演练尤其有用。

审计日志片段（CSV）

timestamp  tool=query  sql="INSERT INTO students (id, name) VALUES (99,'hack')"  rows=0  ok=False
timestamp  tool=get_course_stats  sql="SELECT ... CS205 ..."  rows=4  ok=True  elapsed=0.6ms

实测：非法 INSERT 被拦截后仍被审计记录（ok=False），且数据库行数保持不变——证明不只是"挡住了"，还"留痕了"。

5面向业务的工具，才是它的价值

光有 query（裸 SQL 网关）还不够——那只是一层「安全的壳」。真正对用户有价值的是封装好的业务工具：让不懂 SQL 的 Agent（或用户）直接说业务问题，网关从内部用固定、参数化的语句去查。这样从根上就没有用户输入进 SQL，注入面直接消失：

工具回答的业务问题安全方式
list_tables库里有哪些表、多少行固定元数据查询
describe_table某张表字段 / 类型 / 主键表名白名单校验
query原始只读 SQL（授权 Agent 用）走完整校验器 + 参数绑定
get_student_profile学生画像 + 平均分 + 选课成绩固定参数化语句
get_course_stats课程人数 / 均分 / 及格率固定参数化语句
get_enrollment_summary按年份/学季的选课汇总报表固定参数化语句

这种「仪表盘式的白名单函数 + 一个受控的裸 SQL 逃生口」的组合，其实是数据开放的最佳实践：日常查询走安全封装，特殊需求走受控网关，两边背后的保护完全一致。

实测端到端 demo 里，Agent 调用 get_course_stats 拿到 CS205 真实统计（选课 4 人 / 均分 83.5 / 及格率 75%）；而一条 INSERT 则稳定返回 isError 提示校验未通过——一正一负，两条路径都被验证。

6结论与下一步

  • ✓ 只读由多层面保证：词法校验 + 参数绑定 + 强制 LIMIT + mode=ro，不依赖单一判断
  • ✓ 安全可验证：26 个单测覆盖写防护 / 注入 / 多语句 / 截断 / 鉴权 / 审计
  • ✓ 鉴权审计配套：中间件统一收口 token，审计留痕到每条查询
  • ⚠ 局限：当前是 SQLite 单库；生产化可把网关层接到 PostgreSQL（校验逻辑通用），并接入 MCP 的 OAuth 流程做用户级权限。
下一步方向：把校验器抽象成可插拔「方言后端」（SQLite / Postgres / MySQL）→ 接入 MCP OAuth 实现用户级行权限 → 增加敏感列脱敏 → 加「查询计划预算」拒绝代价过高的 JOIN。这个项目很适合在上面不断堆安全细节，而且每加一层都能配一组测试。
