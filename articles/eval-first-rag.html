检索评测优先的 RAG：
别急着调优，先搞清 检索到底行不行

一句话结论主流 RAG 简历都只证明「能答」，无法回答「检索到底行不行、差在哪、为什么这么调」。这个项目不交付又一个 RAG demo，而是交付怎么证明 RAG 有效的评测资产：517 条固定评测集 + 多策略对比 + 失败归因 + 忠实性校验，一次运行产出可复现的数字。代码在 github.com/Vanity-1/eval-first-rag。

1为什么要评估优先

主流 RAG 简历项目普遍长这样：手搭一个检索 + LLM，喂几句产品文档，贴几张问答截图。面试官一旦追问三个问题就露馅：检索质量怎么量化？为什么这么调融合？失败长什么样？

  • 检索质量怎么量化：连 hit@k、Recall、NDCG 都说不清，只知道"感觉答上了"。
  • 为什么这么调：RRF、双信号融合、源权重，全是抄来的标配，说不出取舍。
  • 失败长什么样：从不记录 miss，说不清是排序问题还是检索缺口。

所以思路反过来：evaluation-first。先把检索质量拆成可比较、可归因、可复现的指标闭环，用一组固定评测集 + 固定策略对比跑出数字，再逐条分析根因。调优是第二步，评测是第一步。

2评测集怎么构建

评测集是整套可信度的地基，分两层构造：

  • 程序化 known-item retrieval（KIR）：从真实目录采样 easy（精确品名）和 medium（属性 + 核心词改写）查询，ground truth 是唯一 product_id。默认 300 + 200 条。
  • 手工 curated hard：政策、跨源、易混淆、噪字查询，gold 是相关集，专测难边界。

相关性用三套 gold 模式，对应三种经典检索评测任务：

gold 模式语义测什么
product_idquery 精确/改写指向唯一产品能否定位已知目标（KIR）
terms相关文档是一组（如所有退货政策）多相关下的 Recall / Precision / NDCG
cross（AND）须同时覆盖政策与产品源才算命中单源永远无法满足 → 多源融合必要性被量化
可复现的关键固定随机种子 42，任何机器重跑 scripts/build_eval_set.py 都得到同一份评测集——这决定了后续所有数字能不能被独立验证。

难度分层 easy → medium → hard 还有一个作用：观察检索在哪个难度开始崩塌，而不是只看一个笼统的平均分。

3三套策略同语料对比

策略必须是同语料、同参数、同一份评测集，唯一变量是融合策略，对比才公平：

  • single：针对性单源（目录查询只检 catalog）
  • plain：多源拼接 keep-first
  • rrf：Reciprocal Rank Fusion 融合

517 条查询跑完，总体 hit@5 最高的反而是 single（91.9%），但这掩盖了真相。按查询类型拆分后，结论完全反转：

type（n）singleplainrrf
catalog 目录（506）92.7%92.7%88.7%
policy 政策（6）100%16.7%100%
cross 跨源（5）0%0%100%

三个发现：

  • known-item 检索 single 才是最优：纯目录定位，针对性单源又快又准，多源融合反而是多余的。
  • plain 会把政策文档挤掉：多源拼接 keep-first，catalog 占满前几名，政策文档（n=6）掉出视野，命中 16.7%。
  • cross 只有 rrf 能救：跨源查询必须同时覆盖政策 + 产品两个源，single / plain 一个源永远不满足，rrf 从 0% 打到 100%——多源融合的必要性由此被量化。
小源偏袒是真实代价policies 只有 8 条，任何查询都会被它排进源内高 rank，融合后对纯目录查询形成噪声——这就是 rrf 的 catalog hit@5 略低于 single 的原因。不是 bug，是融合本身的特性，后续可做源权重 / 查询分类降级缓解。

一句话：单源与多源要分场景，「融合一定更好」是错觉。

4失败归因：把问题分层

只看命中率不知道往哪使劲。把每条 miss 归因成两类：

  • recall_failure：gold 根本没进 top-k（检索缺口，融合也救不了）
  • ranking_failure：gold 在 top-k 里但排位靠后（排序 / 融合的问题）

plain → rrf 的差分是最有意思的部分：

plain → rrf 融合差分

rescues（找回）
5
loses（丢失）
0
both_fail（都检索不到）
37

关键在于 both_fail = 37：plain 和 rrf 都无法命中的查询，才是融合救不回来的真正检索缺口，指向 embedding / 分段粒度 / 同义词，而不是融合策略。把这 37 条拎出来逐条看，比改参数有价值得多。

失败的归因价值在于：先分清「融合该不该背锅」，再去对症下药。37 条 both_fail 指向的是语料/编码层，5 条 rescues 证明融合本身在干活。

5忠实性校验

检索对了，不代表模型不乱编。忠实性校验是可靠性最后一道闸：本地 qwen2.5:3b 基于检索上下文生成回答，再用一个 judge 标注 grounded / partially / ungrounded，结论是否基于给定上下文。磁盘缓存保证可复现。

本机跑 8 例：grounded 7 / 8。唯一一例 ungrounded 非常典型——查询「Toasted Almond Rice Pilaf Mix」的退货政策：

幻觉案例 kir-e-0003模型回答「西班牙米饭混合物是 30 天内可退，所以它也适用同样的退货政策」。可上下文里根本没有这条政策——模型在「合理推断」，但 judge 判定为 ungrounded。这说明：即便 KIR 精确检索命中，生成层照样能引入幻觉，调优不能只盯着检索一条线。

这也是 evaluation-first 的价值所在：把「能答」拆成「检索对」和「答得忠实」两条独立的质量线，每一条都能单独量化、单独报告。

6结论与下一步

  • ✓ 评估优先：先用量化回答「检索行不行」，再谈调优——517 条评测集 + 固定 seed 完全可复现。
  • ✓ 分场景才有真相：known-item 单源最快，跨源非 RRF 不可，「融合一定更好」是不分场景的错觉。
  • ✓ 归因分层：区分「融合能救的排序问题」与「融合救不了的检索缺口」，优化点立刻清晰。
  • ✓ 忠实性独立成线：检索对 ≠ 答得对，幻觉风险单独量化、单独报告。
  • ⚠ 局限：cross/terms 相关事件本身不多（n≤6），统计上偏少，需要更大的跨源评测集来坐实结论。
下一步方向：按查询类型做混合路由（目录走单源快速路径、跨源走 RRF）量化端到端收益 → 源权重 / score-based 融合缓解小源偏袒再回归对比 → BM25 + vector 双信号同语料 RRF → faithfulness 接入 Langfuse 做请求级可观测，联动检索质量。
