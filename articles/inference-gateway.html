1为什么要一层网关

本地部署 ollama 之后，最常见的用法是直接调 /api/chat。单机自己玩没问题，但一旦要接进 Agent 或产品，三个问题会反复出现：

  • 模型选谁：聊天、抽 JSON、要质量，全都打同一个模型。要么大材小用，要么小材大用。
  • 重复计算：Agent 每轮都带着同一段 system prompt 和工具定义，模型每次都要重新处理一遍前缀。
  • 输出不可靠：让模型输出 JSON，它偶尔给你包一层 markdown、多解释两句，或者字段缺一个。

这三个问题都不难单独解决，但散落在调用方代码里，每个 Agent 都要重写一遍。网关层的思路是：把这三件事从调用方抽出来，统一收口。调用方只关心「我要聊天 / 我要 JSON」，网关负责选模型、做缓存、保证格式。

2多模型路由：按任务分流 + 健康降级

路由的核心是一个可插拔的策略接口，四种策略覆盖大多数场景：

策略行为适用
fixed固定一个模型单模型环境
round_robin可用模型间轮询负载均衡
task_based按任务类型路由到具备对应能力的最低优先级模型默认
priority始终用优先级最高且健康的模型主备切换

模型用「能力标签」描述，而不是写死名字：qwen2.5:3b 标 fast，qwen2.5:7b 标 quality。任务类型映射到能力，比如 chat → fast、json → json。这样加新模型只改配置，不动代码。

真正花功夫的是健康降级。网关维护每个模型的连续失败计数：连续失败 3 次标记不可用，进入 60s 冷却，冷却后自动恢复。候选模型全挂时，扩展到全量模型池找一个健康的顶上，而不是把错误直接抛给调用方。

一个容易踩的坑最初实现里，task_based 只认能力标签匹配到的模型。结果「fast」能力只匹配到 qwen2.5:3b 一个模型，它一挂，整个降级逻辑就失效了——因为候选集合里根本没有别的模型。修法是：候选全不健康时，扩大到全量模型池再选。降级逻辑要写在「候选集合之外」，而不是只盯着当前集合。

3提示缓存：响应缓存 + KV 前缀复用

「提示缓存」在网关层拆成两层，收益来源完全不同：

  • 响应缓存：完全相同的请求（模型 + 消息 + 参数）直接返回上次结果。LRU + TTL，命中后延迟从秒级降到毫秒级。适合幂等查询、重复的实体抽取。
  • KV 前缀复用：网关设置 keep_alive 让模型常驻内存，ollama 对相同的 system prompt / few-shot 前缀复用 KV cache，省掉重复的 prompt 处理。

响应缓存是网关自己实现的，收益最直观；KV 前缀复用是「借」ollama 的能力，网关负责把 keep_alive 管理好，并统计共享前缀比例，让收益可观测。

响应缓存命中是「完全相同的请求」才生效，命中率取决于调用方重复度；KV 前缀复用则是「前缀相同」就生效，Agent 场景下几乎每轮都命中。两者不冲突，叠加使用。

4结构化输出：校验、重试、回退

让模型输出 JSON，最稳的办法是 ollama 的 format="json"，但输出仍然可能带 markdown 围栏、前后解释文字，或者字段缺失。网关的处理流程：

步骤做什么失败怎么办
1. 提取容忍 markdown 围栏与杂文本，括号配平定位 JSON带修正反馈重试
2. 校验jsonschema 校验字段类型与必填项带具体错误重试
3. 重试把失败原因拼进 prompt，最多重试 2 次仍失败 → 回退
4. 回退切到备用模型再试一次全部失败 → 返回 422

重试不是简单重发，而是把失败原因作为修正反馈拼进 prompt——「你上一次输出不是合法 JSON：xxx，请重新生成」。实测中，第一次输出缺字段的情况，带反馈重试后基本都能补齐。

实测5 组实体抽取，成功率 100%（5/5），平均 2.2 次尝试，0 次回退。重试机制把「偶发失败」消化在网关内部，调用方拿到的永远是合法 JSON。

6结论与下一步

  • ✓ 三个问题一次收口：选模型、缓存、格式校验，调用方只关心业务。
  • ✓ 收益可量化：缓存命中率、TTFT、结构化成功率都有指标，不是「感觉快了」。
  • ✓ 可复现：41 个单测 + 一键基准脚本，面试能现场跑。
  • ⚠ 局限：多模型路由缺真实对比数据；响应缓存是精确匹配，语义相近的请求不命中。
下一步方向：接入 Langfuse 做请求级可观测 → 加 RAG 检索结果缓存 → 模型健康检查自动降级已实现，可继续做「按负载自动扩缩」→ 把网关抽成可插拔 SDK，让 Agent 框架直接内嵌。
