多源客服系统二开：从「静默失败」到「检索可靠」

这篇讲什么把一个能「跑通」的电商零售开源项目，打磨到「检索可靠、结果可解释、换环境也稳定」。全程踩了 5 类工程坑，重点是那些不报错、但结果不对的隐性故障。

1背景：二开要解决什么

很多电商客服项目的痛点很典型：客服回复依赖人工经验、知识分散在商品目录与政策文档里、退货这类高风险操作不能交给模型完全自主。我基于开源项目做二开，目标是把两件事做扎实：

  • RAG 检索可靠 —— 用户问「有机牛油果」，稳定召回正确商品，并且能讲清出处。
  • 多 Agent 编排可用 —— 销售 / 客服分流 + Human-in-the-loop 退货审批，且全程本地可跑。

2坑一：建库与查询的嵌入模型不一致

静默故障 · 最难定位的一类：「跑得通，但结果空白」

现象：库建好了、数据也在，但无论问什么，相似度检索都返回空或无关结果，而且不报任何错误。

排查：分别打点建库与查询时实际使用的嵌入模型，发现维数对不上：

build_vector_db.py / tools.py# 建库脚本                    # 查询端
model = "mxbai-embed-large-v1"   model = "all-MiniLM-L6-v2"
# 1024 维                       # 384 维
根因Chroma 在 upsert 时用建库模型的向量维数定下集合维度，查询向量维度对不上时，轻则空结果、重则抛 InvalidDimensionException。维度不一致意味着存进去与查询的向量不在同一空间，相似度比较全部失效——而这属于「可运行但结果空白」的静默故障。

解决：把嵌入模型收敛为单一配置源，并加回归测试守卫防止再次漂移：

config.pyEMBEDDING_MODEL = "nomic-embed-text"   # Ollama 本地 · 768 维 · CPU 友好
CHROMA_DIR = "vector_db"
tests/test_embedding_consistency.pydef test_single_embedding_source():
    # 断言建库脚本与查询端都引用 config.EMBEDDING_MODEL，
    # 不允许任何一处硬编码其他模型名。
效果修复后用 10 组典型电商查询（牛油果、酸奶、冷冻披萨……）验证，Top-3 命中率 100%，且换环境不复发。
结论：RAG 的「嵌入一致性」是第一顺位检查项，最好用单一常量 + 测试锁死，而不是靠人工记得。

3坑二：多知识源的「拼接不等于融合」

项目有商品目录（catalog_chunks，9288 条）与政策文档（policies，8 条）两个向量集合。早期实现是「每个源各取 top-k，然后按源顺序拼接」。

问题商品 9288 条、政策 8 条，拼接后商品永远排前面，弱源（政策）的高相关召回被淹没；同一条内容跨源重复召回，上下文噪音多、排序不稳定。完整量化见《RRF 融合对比实验》。

解决：实现 RRF（Reciprocal Rank Fusion）倒数排名融合，聚合多个源的排序信号并天然去重：

agents/tools/rrf_fusion.py# RRF 核心：按「倒数排名」聚合各源排序
# score(doc) = Σ_sources  1 / (rank_in_source + K)   # K=60
def fuse(groups):
    scores = {}; docs = {}
    for group in groups:               # 每个源自己的 top-k
        for rank, doc in enumerate(group):
            key = doc["text"].lower()
            scores[key] = scores.get(key, 0) + 1.0 / (60 + rank + 1)
            docs.setdefault(key, doc)
    return [docs[k] for k, _ in sorted(scores.items(),
                                       key=lambda kv: kv[1], reverse=True)]
效果对比同一批查询：RRF 返回更少的重复噪音、跨源高相关文档排得更前。融合算法抽成独立函数，可脱离服务单独跑单测。

4坑三：chroma 0.5.x 的落盘丢段

检索可靠之后，又遇到存储层的隐性坑：多线程并发 upsert 会让 chroma 0.5.x 丢失 HNSW 向量段——sqlite / pickle 都在，但查询时报 Cannot open header file。

规避方式很直接：把「网络 IO 密集」的嵌入层并发、把「写入层」串行批量：

线程嵌入 + 顺序批量写入with ThreadPoolExecutor(8) as ex:
    vecs = list(ex.map(embed_text, chunk_docs))   # 并发取 embedding
col.add(ids=ids, embeddings=vecs, documents=chunk_docs)  # 顺序 add

这也是最终让我改用预计算嵌入缓存 + 内存余弦检索的原因之一——避免单机持久化不可控，让检索在任何环境都稳定可复现。

5坑四：Agent 编排框架的 API 迁移

项目里旧示例基于已停产的 adk 包，官方新版本是 google-adk，API 变了：

# 旧（已停产）                    # 新（官方）
from adk.tools import Tool         from google.adk.agents import Agent, SequentialAgent
                                   from google.adk.tools import FunctionTool

迁移时踩到细节：SequentialAgent 只接受 sub_agents，tools 参数属于 Agent / LlmAgent——照文档写会直接报参数不支持。

教训升级第三方大版本时先查官方迁移文档，别照搬旧写法；用最小用例验证 API 签名，不要一次性全量改。

这些坑的共同点：都是「能跑但结果不对 / 换环境就挂」的隐性工程问题，单靠功能测试覆盖不到，需要专门的检索评估与回归测试来兜底。这也是二开这类项目最有价值的部分——不只是把功能做出来，而是把可靠性夯实。
